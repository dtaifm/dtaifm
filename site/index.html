Deterministic-first AI middleware

AI proposes.
The deterministic layer disposes.

dtaifm treats an LLM as an advisor, never an executor. The model emits a candidate artifact; a rigid, human-written validator must approve it before anything runs. AI output is an artifact, not an action.

The trust boundary

Three layers, one contract

Humans define hard constraints. The AI teacher proposes candidate rules. A deterministic validator decides what is allowed — and only approved rules ever reach the runtime.

def by humans
Constraints
Hard rules in YAML. Immutable at runtime, never written by AI.
AI side · untrusted
Teacher.propose()
An LLM (or mock) returns a portable candidate RuleSet — an artifact, nothing more.
deterministic gate
Validator → Runtime
Approves or rejects each rule against the constraints. Only approved rules execute.

▲ everything left of the gate is a proposal · everything right of it is deterministic, auditable execution

Why it matters

Decouple the thinking from the doing

A raw LLM in your runtime hallucinates parameters, spirals in agent loops, and can be steered by prompt injection. dtaifm puts a deterministic gate between the model and your system — so you get AI-level flexibility with deterministic-level safety.

Prompt-injection containment

Even if a malicious prompt fully captures the model, the worst it can emit is a candidate artifact. The validator still has to approve it — and refuses anything that breaks a hard constraint.

Compliance guardrails

Regulatory limits, financial caps, and business rules are enforced in hard-coded validators, not coaxed from a prompt. A proposal that violates one is blocked — predictably, every time.

Safe rule & config generation

Nothing the AI generates — routing tables, policies, transformation rules, lightweight scripts — reaches your runtime until it clears automated validation.

Full auditability

AI output is a static artifact, so every propose → validate → execute cycle is traceable, replayable, and verifiable with SHA-256-hashed audit bundles.

The shift

Advisor, not executor

Traditional agentic AI lets the model act. dtaifm lets it only propose.

Traditional agentic AI
  • Executor — translates intent straight into tool and API calls
  • Reactive — guarded by prompt engineering and output filters (probabilistic)
  • Hallucinated or injected actions can reach the system
dtaifm
  • Advisor — proposes a candidate artifact, nothing more
  • Proactive — guarded by hard-coded deterministic validators (predictable)
  • Unapproved output never executes — blocked unless it clears every constraint

In the box

Batteries included, provider-agnostic

A small, dependency-light core (just PyYAML) with optional adapters and example domain packs. Bring your own model and your own domain.

5 teacher adapters

mock, Anthropic, OpenAI, Ollama, and Lemonade — cloud or fully local, behind one provider-neutral contract. Every adapter is a translator, never a trusted component.

Domain packs

Ships smart_home and network_automation to demonstrate the pattern. Define your own vocabulary and constraint evaluators.

Audit bundles & replay

Self-contained .dtaifm-review.json artifacts with canonical-JSON SHA-256 hashes. dtaifm replay re-verifies and catches tampering.

Versioned schemas

Every file carries schema_version with published JSON Schemas, so producers and consumers can evolve independently.

Get started

One command, the whole pipeline

The demo walks propose → validate → execute → bundle → replay and prints a step-by-step report. Runs fully offline with the mock teacher — no API key needed.

# install from PyPI
$ pip install dtaifm

# run the full pipeline (offline)
$ dtaifm demo smart_home

# try the second domain, or a local model
$ dtaifm demo network_automation
$ dtaifm demo smart_home --teacher ollama --model llama3.2

Then explore

The demo leaves the proposed rules, the audit bundle, and the hashes in a temp dir so you can inspect and replay them.
